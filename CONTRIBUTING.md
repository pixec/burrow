# Contributing to Burrow

## Before you start

Please keep no more than two pull requests open at a time. Reviews go faster that way, and once your first one lands, the next ones tend to go smoothly. Pull requests stacked on each other also go stale quickly as `main` moves.

For a new feature or anything that changes the API, open an issue first and wait for a maintainer to agree on the approach before writing code. It saves you from building something we can't take.

Found a security issue? Please report it privately through GitHub's private vulnerability reporting, not in a public issue.

### Things we probably won't merge

- Changes to the public API, CLI or SDKs that nobody agreed on first
- Features whose complexity outweighs what they give users
- Large refactors
- Non-trivial changes without tests
- Style-only changes that don't change behaviour
- Code generated by an AI tool that you don't fully understand

### Pull requests we love

- Fixes to the documentation
- Bug fixes, ideally with a test that fails without them
- Small improvements to a hypervisor, guest OS or SDK
- Issues a maintainer has marked as open for contributions

## AI policy

Using AI tools is fine, but you're responsible for every line you submit, and you should understand it as well as if you'd written it yourself. We don't accept pull requests opened by autonomous agents, and we may close them without comment.

Please write pull request descriptions, issues and replies yourself. If you use a tool to translate, put the translation in a quote block followed by your original text.

## Sending changes

Build Burrow and try your change before opening a pull request. You'll need Rust (the version in `rust-toolchain.toml`), Docker, and Linux with KVM for anything that boots a VM. On an Apple Silicon Mac with nested virtualization (M3 or later, macOS 15 or later), you can run the whole stack inside a Colima VM:

```sh
colima start burrow --vm-type vz --nested-virtualization --cpu 4 --memory 8 --disk 40
docker --context colima-burrow compose -f deploy/dev/compose.yaml up -d --build
```

CI runs these, so run them first:

```sh
cargo fmt --all --check
cargo clippy --workspace --all-targets -- -D warnings
cargo test --workspace
scripts/sync-protos.sh --check
```

If you touched the SDKs or the protos, also run:

```sh
(cd sdk/typescript && npm ci && npx tsc --noEmit && npm test)
(cd sdk/python && pip install -e '.[dev]' && pytest && python scripts/genproto.py --check)
```

After changing a `.proto` file, run `scripts/sync-protos.sh` to update the SDK copies, then regenerate the Python modules with `python sdk/python/scripts/genproto.py` on Python 3.9 with the pinned `grpcio-tools`.

When you open your pull request:

- Keep it to one change.
- Give it a [conventional commit](https://www.conventionalcommits.org) title, such as `fix: end exec streams at exit`.
- Say what you tested, and include timings for anything that touches performance.
- Update the [documentation](https://burrow.pixec.net) if users will notice the change.
- Sign the CLA (below).

Opening a pull request doesn't guarantee it will be merged, even after a lot of work, and messaging maintainers directly won't speed up a review.

## Signing the CLA

The first time you open a pull request, a bot will ask you to sign the [Contributor License Agreement](CLA.md). You only do this once. To sign, reply on the pull request with:

```text
I have read the CLA Document and I hereby sign the CLA.
```

If the check doesn't update, comment `recheck`. If your employer owns the code you write, they need to sign too. Ask them to email oss+burrow@pixec.net.

You keep the copyright in your work. The CLA gives Pixec Technologies permission to use and share it, including under licenses other than the AGPL-3.0.
